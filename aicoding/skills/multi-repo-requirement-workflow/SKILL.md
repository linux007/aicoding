这是一个**总控 workflow skill**，作用不是直接实现功能，而是把 Claude 拉到正确阶段。

适用场景：

- 用户拿来一份复杂需求文档，希望先做技术方案
- 需求涉及多个仓库、多个系统边界或多个子能力
- 用户希望 Claude 像熟悉项目的资深研发一样推进，但不希望一上来就写代码

不适用场景：

- bugfix
- typo / 文案修改
- 单仓小范围配置调整
- 用户明确说“直接改代码，不要走方案流程”

---

## 核心原则

1. **先理解项目，再理解需求，再写方案，最后编码**
2. **先做需求收敛，不直接写长篇技术方案**
3. **先拆子方案，只让一个子方案进入 OpenSpec**
4. **边界没锁定前，不允许进入实现阶段**

---

## 触发词与入口信号

出现以下任一信号时，优先使用本 skill：

- “我现在有一个涉及多个 git 仓库模块交互的项目”
- “请先根据需求文档生成技术方案文档”
- “不要直接写代码”
- “先帮我做需求收敛 / 方案拆分”
- “希望你像熟悉项目的资深研发一样推进”
- “先做 proposal / design，再开发”

如果用户同时提到多仓、需求文档、技术方案、不要直接实现，本 skill 的优先级高于普通实现类 skill。

## 真实输入示例

以下输入通常应触发本 skill：

- “我现在有一个涉及多个 git 仓库模块交互的项目，对于新增需求，希望你先根据需求文档生成技术方案文档，再完整准确完成开发。”
- “这是一份复杂需求文档，请不要直接写代码，先帮我做需求收敛、方案拆分，再决定怎么进入 OpenSpec。”
- “我不熟悉这个多仓项目，你像资深研发一样帮我推进，但先别实现，先做 proposal/design。”

以下输入通常**不应**触发本 skill：

- “帮我修这个接口的参数校验 bug。”
- “给这个函数加一条日志。”
- “直接把这个字段改成必填。”

## 标准流程

### Phase 0：确认目标工作模式

先确认：

- 目标仓库集合是不是当前聚合仓及其子仓
- 需求输入是否来自固定模板文档 / issue / 聊天记录
- 用户当前最想优先解决的是：方案生成、开发执行，还是端到端流水线

如果这些问题不明确，先问清楚，不要进入代码探索。

### Phase 1：项目级探索

先读：

- 根目录 `CLAUDE.md`
- `openspec/` 和已有 changes / specs
- `docs/` 中已有工作流或方案文档
- GitNexus 项目 / group 级上下文（如果可用）

目标是输出一段“项目工作模式结论”，回答：

- 当前项目更适合怎样的需求推进方式
- 是否已经具备 OpenSpec / GitNexus / 项目级约束
- 需求应该先在聚合仓收敛还是先进入单个子仓

### Phase 2：需求收敛

调用 `requirement-intake` skill，输出四段式中间产物：

1. 需求压缩摘要
2. 现状映射
3. 缺口清单
4. 子方案拆分建议

**禁止**在这个阶段直接写 proposal / design / 代码。

**停止条件：** 四段式产物输出完成后，必须停下来等待用户确认或进入 Phase 3；不得自动跳入 OpenSpec。

### Phase 3：子方案选择

从拆分结果中只选一个子方案继续推进。

**停止条件：** 如果用户没有明确接受推荐子方案，就停在这一阶段，不得自动创建 change。

优先选择：

- 边界最清晰
- 能独立落盘
- 能给后续提供稳定上游输入
- 跨仓风险最可控

如果用户没有指定，就给出推荐顺序和理由。

**额外要求：** 如果选中的首个子方案属于“配置管理 / 资产管理 / 平台后台能力”，在进入下一阶段前，必须检查这 3 类设计点是否已经收敛：

1. 数据表 / 实体结构方案是否锁定（如单表 JSON、单表多 JSON 字段、主子表）
2. 唯一性与主键口径是否锁定（如 teacher_id + ratio 等组合约束）
3. 接口契约层级与关键字段是否锁定（仅后台 CRUD、后台 CRUD + 来源契约、或更大范围；请求/响应字段至少覆盖主键、展示字段、筛选字段、预览字段、状态字段）

如果这三类问题仍未锁定，则该子方案只能停留在“继续收敛”，不得直接视为可进入 OpenSpec。

### Phase 4：进入 OpenSpec

当且仅当以下条件成立时，才建议或桥接到 `/opsx:propose`：

1. scope 已锁定
2. 主要设计分叉已决策
3. 跨系统依赖至少已经映射出来
4. 验收标准可描述
5. 当前对话已经开始收敛，而不是继续扩散

如果任一条件不成立，回到前一个阶段继续收敛。

**针对配置管理 / 资产管理 / 平台后台类子方案的补充门槛：**
在满足以上 5 条之外，还必须额外确认：

6. 数据表 / 实体结构已经收敛到可落盘的粒度
7. 唯一性规则和主键口径已经可描述
8. 接口契约层级已经锁定，且关键请求/响应字段已经能够列出

如果 6-8 任一不成立，不得直接桥接 `/opsx:propose`。

**额外硬约束：** 本 skill 不得在未获得用户对“首个子方案”的明确认可前，自动建议或桥接 `/opsx:propose`。

---

## 输出要求

在不同阶段，输出应分别是：

- Phase 1：项目工作模式结论
- Phase 2：四段式中间产物
- Phase 3：推荐的首个子方案及边界
- Phase 4：明确告诉用户“现在适合进入 OpenSpec”，并建议或桥接 `/opsx:propose`

如果首个子方案属于配置管理 / 资产管理 / 平台后台能力，Phase 3 或 Phase 4 的输出里还应显式补一句：

- 当前是否已经锁定表结构方案
- 当前是否已经锁定接口契约层级与关键字段口径

不要默认把这两件事留到 proposal/design 阶段再临时补。

---

## Guardrails

- 不要一上来就进入某个子仓写代码
- 不要把页面原型复述当成技术方案
- 不要把多个子方案混成一个大 change
- 不要在需求边界未锁定时创建 proposal
- 如果用户明确要求只做分析，就停在分析阶段

---

## 推荐话术

当完成 Phase 2 或 Phase 3 后，可以这样总结：

> 当前这份需求更适合先拆成多个技术子方案，而不是直接写一篇大方案。
> 我建议先推进 `<子方案名>`，因为它边界最清晰，且能给后续能力提供稳定上游。
> 如果你认可，我下一步就直接进入 `/opsx:propose`，把这个子方案正式落成 proposal / design / spec / tasks / plan。
